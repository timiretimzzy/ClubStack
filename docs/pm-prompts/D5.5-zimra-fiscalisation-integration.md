AUTHORITATIVE ZIMRA REFERENCE
==================================================

The attached Fiscal Device Gateway API Specification v7.2 is also authoritative for the fiscalisation behavior.

Relevant requirements include:

- Device registration and certificate acquisition
- Fiscal day lifecycle
- Receipt submission
- Offline fiscalisation/file submission
- Fiscal day closure
- Receipt signatures
- Fiscal counters
- Invoice/credit/debit note handling
- FDMS response/signature handling

The specification states that fiscal devices can operate in Online or Offline modes, with online receipt submission through submitReceipt and offline receipt/file submission through submitFile. :contentReference[oaicite:1]{index=1} :contentReference[oaicite:2]{index=2}

The fiscal day lifecycle is:

FiscalDayClosed
→ openDay
→ FiscalDayOpened
→ submit receipts
→ closeDay
→ FiscalDayCloseInitiated
→ FiscalDayClosed / FiscalDayCloseFailed. :contentReference[oaicite:3]{index=3}

A receipt submission produces a receiptID, server date and FDMS receipt signature which must be retained by the fiscal device. :contentReference[oaicite:4]{index=4}

Do not implement these rules independently if FiscalStackZW.dll already encapsulates them. Reuse the DLL's proven implementation.

==================================================
OFFLINE SUPPORT
==================================================

Determine exactly how FiscalStackZW.dll and FiscalStackZWPOS.App handle offline fiscalisation.

Do not replace it with a custom offline mechanism unless the existing DLL genuinely lacks the required capability.

The ZIMRA specification supports offline operation where receipts are stored by the fiscal device and subsequently submitted via files when connectivity returns. :contentReference[oaicite:9]{index=9}

ClubStack is already designed as a local-first operational platform.

The fiscalisation integration must therefore not destroy ClubStack's ability to operate locally when FDMS connectivity is unavailable.

If fiscalisation is temporarily unavailable:

- preserve the ClubStack transaction
- retain the fiscalisation work required
- make the fiscalisation state explicit
- retry according to the proven FiscalStackZW behavior
- never silently mark an unfiscalised transaction as fiscalised

==================================================
FAILURE HANDLING
==================================================

External fiscalisation calls must NOT corrupt the ClubStack sale transaction.

Do not hold a PostgreSQL transaction open while waiting unnecessarily for a network call.

Do not make the external FDMS call part of a database transaction that assumes atomic external completion.

Use ClubStack's existing outbox/retry architecture where appropriate.

The system must distinguish at least:

- not required
- pending
- submitted
- fiscalised
- failed/retryable
- failed/non-retryable

Use the actual working FiscalStackZW error behavior as the reference.

Do not invent arbitrary error classifications when the DLL already exposes meaningful states/errors.

==================================================
IDEMPOTENCY
==================================================

D5 already has hardened idempotency behavior.

Fiscalisation MUST NOT cause duplicate fiscal documents when:

- the cashier retries completion
- the application retries after a timeout
- the server retries an outbox operation
- the FDMS request was accepted but the response was lost
- the same fiscalisation operation is replayed

The ZIMRA specification itself states that submitting the same receipt more than once with the same deviceID, receiptGlobalNo and receiptHash returns the original fiscal result rather than creating another receipt. :contentReference[oaicite:10]{index=10}

Reuse that property and the existing ClubStack idempotency mechanisms.
