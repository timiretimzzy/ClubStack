## Carried decisions (do not re-litigate)

- ClubStack monetary and tax values are authoritative. The device is a fiscalisation
  and reporting sink, not a pricing source of truth.
- Never silently re-price, re-rate, re-round, or substitute a device-computed amount.
- Never implicitly open a fiscal day.
- Preserve the tender breakdown while sending aggregate currency XML.

## Directive

Finalize D5.5 for acceptance. Close every non-live gap that can be closed honestly,
verify the real configuration and live environment, and do not claim live verification
that was not obtained.

## 1. Refund tax is a correctness and compliance issue, not cosmetic

A full refund must reverse the tax the invoice actually charged. Implement the most
defensible treatment supported by the existing data, rather than a guess:

- Where the original sale lines carry tax treatment, rate, and per-line tax amount,
  the credit note uses the original treatment and rate for each refunded line and
  credits the same tax amount.
- Where historical snapshots lack that data, apply the most defensible fallback and
  state clearly in the report what it is and why.
- Where the data is internally inconsistent, do not invent a reconciliation. Persist
  the document as failed with a reason an operator can act on.
- A mixed-rate invoice must produce a credit note that credits each bracket separately.

## 2. Device tax rate handling

Confirm how the engine maps ClubStack tax brackets to device tax IDs. If the mapping
turns out to be a defect, correct it in ClubStack; do not work around it by
misrepresenting rates to the device.

## 3. Real configuration review

- Read the real `config.ini` for the device, without printing, copying, logging, or
  auditing any license key, activation key, private key, certificate private material,
  or other credential.
- Verify the configured endpoint, device identity, taxpayer identity, tax table,
  and whether the certificate folder exists outside the application installation
  directory.
- Report any inconsistency found between ClubStack's assumptions and the real
  configuration, and state whether it blocks live verification.

## 4. Verify tax ID resolution

Add deterministic tests proving the resolver cannot select a bracket whose name
indicates zero-rated or exempt when the document requires standard-rated tax. If the
live configuration would break this, fix the logic and say so in the report.

## 5. Refund integrity

- One refund can produce exactly one fiscal credit note. A second attempt for the
  same refund must be rejected, not create a duplicate document.
- Prove a normal invoice is unaffected by the refund-specific changes.
- If the persistence model can carry a refund reference, enforce referential
  integrity in the database, not only in application code.

## 6. Failed fiscalisation must be recoverable

- Rejecting a document with a retryable error must be recoverable by an authorised
  operator without creating a duplicate fiscal document.
- A rejected or failed document that still holds a device receipt must be
  re-drivable and must not be permanently stuck.
- If the engine reports a document as already accepted, reconcile through the engine
  queue instead of transacting the same invoice number twice.
- A document that has already reached `Fiscalised` must be a no-op on retry.
- Repeating the operation must be safe.

## 7. Entity completeness

Confirm the fiscalisation record stores everything needed for audit: device and day
identifiers, fiscal status, receipt and verification references, signatures, QR
payload, submission and completion timestamps, and any field required for retry.

## 8. Deterministic proof

Use a controllable test seam for the device boundary. Cover the failure, retry,
duplicate, and idempotency cases deterministically rather than relying on timing.

## 9. API authorisation and route coverage

- For every fiscalisation route, prove with a real request test: anonymous is
  rejected `401`; an authenticated user without the required permission is rejected
  `403`; the authorised role succeeds.
- Do not rely on inspecting attributes to reach that conclusion.

## 10. SPA acceptance

Confirm an operator can see, from the browser: device status, fiscal day state, the
fiscalisation result for a sale, pending and retry state, and errors that are
understandable. Confirm sensitive device configuration and management controls are
not exposed to ordinary cashiers, that a retry control appears only where the
permission allows, and that a sale receipt can expose the fiscal information.
Confirm no secret is ever rendered in the browser.

## 11. Full regression

- Re-run the full solution build and the full test suite.
- Re-run the D5.5 targeted suite and the SPA build.
- Re-confirm D5 behaviour is unchanged and that no D6-D7 work was introduced.
- Publish nothing into `src/ClubStack.Api/wwwroot` unless that was already the
  established convention.

## 12. Live FDMS verification

Attempt live verification only if a valid licensed device, a valid activation key, a
valid taxpayer configuration, and a valid certificate are all available. Verify
device status, fiscal day handling, and a real fiscalised document if and only if
those prerequisites are genuinely met. Do not fabricate identifiers, values, or
results. Do not send a fabricated taxpayer identity to a production endpoint.

## 13. Honest status and blockers

If live FDMS verification cannot be completed, report exactly which prerequisites
are missing. State which parts of this directive are fully verified, which are only
partially verified, and which remain blocked.
