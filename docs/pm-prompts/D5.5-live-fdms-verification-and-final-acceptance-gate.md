evidence of registration or authentication.

activation not validated; taxpayer/device not registered; tax configuration still

### Part 3 — Device verification

If the device is genuinely provisioned, run the existing empirical device tests and verify
through the real FiscalStackZW.dll: device status, taxpayer information, device
configuration, certificate presence, fiscal day status, configured tax identifiers. Label
these `[EMPIRICAL]`. Do not call them `[LIVE-FDMS]` yet.

### Part 4 — Live fiscal day

On the provisioned device, verify fiscal-day status. If the fiscal day is already open, DO
NOT blindly open another. If closed and the authorized operational procedure permits
opening, open the fiscal day through the existing ClubStack fiscalisation implementation and
verify the resulting state, recording fiscal day number, state, and open timestamp. Do not
expose credentials.

### Part 5 — Controlled live sale

Perform ONE controlled, low-value test sale using a real registered device and a clearly
identified test product appropriate for the taxpayer environment. The sale must use the
existing ClubStack D5 POS flow. Verify: ClubStack sale → fiscalisation requirement →
fiscalisation worker → FiscalStackZW.dll → FDMS → fiscal result → persisted fiscal record →
receipt. Capture, without exposing secrets: ClubStack sale reference; invoice number; fiscal
day number; receipt global number; receipt ID; operation ID; fiscalisation status; FDMS
response/result; server signature presence; and QR information where appropriate. Label the
entire result `[LIVE-FDMS]`. Do not call a local/offline pending result successful.

### Part 6 — Live tax verification

Compare: ClubStack-calculated tax; tax values supplied to FiscalStackZW; tax result
returned by the fiscal engine; and tax result accepted by FDMS. The previous report
observed an engine tax calculation discrepancy. Do NOT change ClubStack's authoritative tax
calculation to make the values match. Determine what actually happens on a registered live
device. If there is a real incompatibility, STOP and report the exact discrepancy and where
it occurs. Do not invent a tax rule.

### Part 7 — Live receipt verification

Confirm the fiscal result can be retrieved through ClubStack. Verify fiscal status, fiscal
day number, receipt global number, QR information, fiscal identifiers, and receipt display.
Verify that no secret appears in the API response or browser.

### Part 8 — Live credit note

Only after the original live sale has succeeded, perform ONE controlled full refund of that
sale. The resulting fiscal document must be a credit note referencing the original invoice.
Verify original invoice reference, credit note fiscal result, tax reversal, fiscal day,
receipt global number, FDMS result, ClubStack refund, and fiscalisation persistence. For a
mixed-rate test, only perform it if the live environment and test data safely support it.
Otherwise the single controlled full refund is sufficient for the live smoke test.

### Part 9 — Live retry / duplicate safety

DO NOT deliberately create duplicate fiscal documents. Where the environment safely permits
it, verify one retry/replay path after a successful fiscal result. Expected behaviour: no
second fiscal document; original fiscal result retained; ClubStack record remains
Fiscalised; worker remains idempotent. If a safe live retry cannot be induced, verify this
through the existing deterministic test seam and report that distinction clearly.

### Part 10 — Live fiscal day close

After the controlled tests, close the fiscal day using the existing fiscalisation
implementation, only if doing so is appropriate for the test device. Verify closure
initiated, final fiscal-day result, final counters where available, final FDMS signature
where available, and the ClubStack stored result. If close fails, DO NOT hide the failure.
Record the exact reason and leave the device in the correct recoverable state.
