You are continuing ClubStack D5.5 from `D5.5_Live_Verification_Session_Report.md`. Read

### Critical PM instruction

A test fiscal device has now been provisioned for D5.5 verification. The supplied test
device identity, activation key, FiscalStack license, and TEST environment are
authoritative for this D5.5 test session. (The credential values are deliberately not
reproduced in this archived copy; they were supplied in-session and must never be written
to a file, report, log, audit row, API response, frontend, source code, or test output.)

### Absolute integration rule

You MUST use the ClubStack implementation to perform the complete fiscalisation lifecycle.
Do NOT directly call ZIMRA/FDMS endpoints. Do NOT use curl. Do NOT use Postman. Do NOT
write a separate REST client. Do NOT call ZimraDirectApi directly from the verification
workflow. Do NOT bypass the ClubStack fiscalisation abstraction. Do NOT manually call
verifyTaxpayerInformation, registerDevice, openDay, submitReceipt, closeDay, or any other
ZIMRA endpoint directly from the agent/session.

The only valid path is: ClubStack -> ClubStack Fiscalisation Service -> ClubStack
Fiscalisation Gateway -> FiscalStackZW.dll -> configured test environment. The test is
successful only if the entire chain works without bypassing ClubStack. We are testing
whether ClubStack's implementation actually works, not whether a manually constructed
ZIMRA request works.

### Primary objective

Using the supplied test device: configure the FiscalStackZW engine through ClubStack;
activate/configure the license through ClubStack; register the fiscal device through
ClubStack; obtain and apply the device configuration through ClubStack; obtain/install any
required certificate through the existing ClubStack/FiscalStack integration; read device
status through ClubStack; read taxpayer/device configuration through ClubStack; verify
fiscal-day state through ClubStack; open the fiscal day through ClubStack; submit a real
test sale through the ClubStack POS; allow ClubStack's fiscalisation worker to submit it
through FiscalStackZW.dll; verify the resulting fiscal record in ClubStack; verify
receipt/fiscal information in ClubStack; perform a controlled refund through ClubStack;
verify the credit note through ClubStack; verify retry/idempotency behavior through
ClubStack; close the fiscal day through ClubStack; verify the final fiscal state through
ClubStack. The test is successful only if the entire chain works without bypassing
ClubStack.

### Part 1 — Test environment configuration

Inspect the existing ClubStack fiscalisation configuration. Do NOT manually edit
`C:\ProgramData\FiscalStackZW\config.ini` unless the ClubStack implementation itself
explicitly requires configuration to be written there as part of its normal device
administration workflow. Use the ClubStack device administration functionality to configure
the test device with the supplied device id, activation key, serial, license, and test
environment. The objective is to prove that the ClubStack administrative workflow can
configure the FiscalStack device correctly. If ClubStack currently exposes configuration
methods/API for license, device ID, serial, activation, environment, and device settings,
use those. Do not bypass them.

### Part 2 — License activation through ClubStack

Use the existing ClubStack fiscalisation administration implementation to apply the
supplied FiscalStack license. Do not disable license validation, patch the DLL, modify
LicenseCore, write the license directly to a file manually, inject a fake license state, or
change the license verification logic. The test should prove ClubStack receives the
license, passes it to FiscalStackZW.dll, and FiscalStackZW reports a valid/active state.
Record the result without printing the actual license. The license must not appear in
report, log, audit, API response, frontend, or test output.

### Part 3 — Device registration through ClubStack

Use the ClubStack fiscalisation service to register/configure the test device. The flow
must remain ClubStack API/service -> FiscalStackZW gateway adapter -> FiscalStackZW.dll ->
test fiscal environment. Do not call a ZIMRA registration endpoint directly. Verify through
ClubStack that the device is recognized, taxpayer configuration is returned, device
configuration is returned, certificate setup completes if required, and the fiscal device
becomes usable. If registration requires asynchronous processing, wait/poll using the
ClubStack implementation. Do not manually hit FDMS endpoints.

### Part 4 — Device status

Use the ClubStack fiscalisation API/service to retrieve device status, device ID, serial,
taxpayer information, fiscal configuration, certificate state, test environment, and
fiscal day status. Verify that ClubStack receives and persists/returns the expected
non-secret information. Do not expose the activation key, license, private key, or
certificate private material.

### Part 5 — Tax configuration

After ClubStack registers the device, retrieve the fiscal configuration through
ClubStack. DO NOT manually invent tax IDs. DO NOT manually overwrite tax rates. Use the
test environment's actual configuration returned through the FiscalStackZW integration.
Verify standard-rated tax ID, zero-rated tax ID, exempt tax ID, tax names, tax rates,
duplicate IDs, and validity. The previous development environment had a broken tax table.
Determine whether the TEST environment is coherent. If it is coherent, use it. If it is
incoherent, STOP before fiscalising a sale and report the exact problem. Do not "fix" tax
IDs by guessing.

### Part 6 — Fiscal day

Use ONLY the ClubStack fiscalisation implementation. First GET fiscal day status through
ClubStack. If the day is closed and opening is required, OPEN the fiscal day through
ClubStack. Do not call FDMS directly. Verify fiscal day number, fiscal status, open
timestamp, and returned operation/result. Do not blindly open a second fiscal day.

### Part 7 — Controlled live test sale

Create exactly ONE controlled test sale through the ClubStack POS. Do not construct a
separate fiscal receipt manually. Use ClubStack POS -> D5 Sale -> Complete Sale ->
Fiscalisation requirement -> Outbox -> Fiscalisation processor -> FiscalStackZW.dll -> TEST
FDMS. Use a simple low-value test product, the actual ClubStack pricing and tax
calculation, and a simple payment method first. Then verify a second case for any
applicable payment variation. The first objective is proving the basic fiscalisation path.

### Part 8 — Fiscal result verification

After the sale, use ClubStack to retrieve the fiscalisation document and verify ClubStack
sale ID, invoice number, fiscalisation status, fiscal day number, receipt global number,
receipt counter, receipt ID, operation ID, QR information, device signature/hash where
available, server/FDMS signature where available, submitted timestamp, and fiscalised
timestamp. Confirm that the fiscal result is actually persisted in the ClubStack database.
Do NOT infer success merely from an empty pending queue, a successful method call, a local
receipt, or a DLL response without a fiscal result. The existing receipt-gated
silent-fiscalisation fix remains mandatory.

### Part 9 — Fiscal status in POS

Verify the ClubStack POS displays the fiscal result correctly. The cashier should see the
operational result, not raw FDMS implementation details. Verify that fiscalised state
displays correctly, pending state displays correctly, failures display correctly, the
receipt can be retrieved, and QR information is available where returned. No secret may
reach the browser.

### Part 10 — Tax verification

Compare all four layers: ClubStack calculated tax; tax supplied to FiscalStackZW; tax
returned/processed by the fiscal engine; and tax accepted by the test fiscal environment.
Record the actual values. Do not alter ClubStack's authoritative accounting/tax values
merely to make the external system agree. If the test environment exposes a genuine
fiscal/tax discrepancy, STOP and report it precisely.

### Part 11 — Payment tests

The previous reference application collapsed payment representation at the fiscal engine
level. ClubStack must continue preserving its own tender breakdown. Verify at least cash,
card, member account where applicable, and split payment if supported by the test
environment. For each: ClubStack must preserve the original tender details; FiscalStackZW
may use its supported aggregate representation; the mapping must remain auditable. Do not
modify D5 payment semantics.

### Part 12 — Credit note

After the original test sale has successfully fiscalised, perform ONE controlled full
refund through ClubStack. The refund must travel through ClubStack refund ->
fiscalisation requirement -> FiscalStackZW.dll -> test FDMS. Verify original invoice
reference, credit note, fiscal day, receipt/global number, fiscal result, tax reversal,
ClubStack refund state. Do not call the ZIMRA credit-note endpoint directly.

### Part 13 — Retry / idempotency

Verify the ClubStack retry implementation. Do not intentionally create duplicate fiscal
documents. At minimum verify: a Fiscalised document retry is a no-op; an engine-held
document is reconciled; a non-accepted document is not marked fiscalised; repeated worker
processing does not change fiscal identifiers; the ClubStack idempotency key remains stable
for the same operation. Use the real test fiscal environment where safe. Use the
deterministic test seam where deliberately inducing a live failure would risk duplicate
documents. Clearly label the result.

### Part 14 — Fiscal day close

Only after the controlled test sale/refund verification, close the fiscal day through
ClubStack. DO NOT call closeDay directly. Verify through ClubStack: close initiated, close
response, final fiscal day status, final counters, final server signature where available,
and stored fiscal-day information. If the test environment requires polling, poll through
the ClubStack implementation.

### Part 15 — No direct ZIMRA access

This rule is absolute. The agent must NOT use curl, Postman, ad-hoc PowerShell REST
requests, a separate HTTP client, ZIMRA endpoints outside FiscalStackZW.dll,
`ZimraDirectApi` as a substitute for ClubStack, hand-built JSON, or bypass the ClubStack
FiscalisationService or FiscalStackZWDllGateway. The only acceptable integration path is
ClubStack -> FiscalisationService -> FiscalStackZWDllGateway -> FiscalStackZW.dll -> TEST
environment. The test must prove that this path works.

### Part 16 — Regression

After the full test sequence, run `dotnet build "ClubStack.slnx"`, `dotnet test
"ClubStack.slnx"`, and `npm run build`. Target 0 warnings, 0 errors, 0 failed tests, 0
skipped tests. Report exact totals. Compare against 477 passed, 0 failed, 0 skipped.

### Part 17 — Security

NEVER print or store the activation key, fiscal license, private key, certificate private
material, or authentication token. The test credentials must not appear in the report. The
activation key must never reach the SPA. The license must never reach the SPA. Do not
place the provided credentials in source code.

### Part 18 — Final acceptance gate

D5.5 is READY FOR PM ACCEPTANCE only if: ClubStack successfully configures the test
device; successfully applies the test license; successfully activates/registers the
device; successfully reads device status; successfully retrieves test tax configuration;
successfully opens a fiscal day; successfully fiscalises a real test sale; persists the
real fiscal result; displays the fiscal result; successfully fiscalises a
refund/credit note; retry/idempotency behavior is verified; successfully closes the fiscal
day; full regression remains green; no direct ZIMRA endpoint was called outside
FiscalStackZW.dll; and no secret was leaked. If any condition fails: D5.5 NOT READY FOR PM
ACCEPTANCE, listing the exact blocker.
