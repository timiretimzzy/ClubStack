## 7. FiscalStackZWPOS.App integration findings `[INSPECTION]`

Public surface actually used, via `src\Services\FiscalStackZWDevice.cs`:

2. **Types used** — one singleton adapter `FiscalStackZWDevice` wrapping

3. **Initialisation** — singleton created in `App.xaml.cs:102`; DLL constructor
   creates `%ProgramData%\FiscalStackZW\config.ini` and `%ProgramData%\FiscalStackZW\<deviceId>\Stack.db`.
4–7. **Configuration / registration / activation / certificates** — `ConfigStore.cs`
   (15,495 b) mirrors `config.ini`; `CertificateWizardFlow.cs` obtains and installs
   client certificates via `ZimraDirectApi.DownloadServerCertificate`
   (`CertificateWizardFlow.cs:163`) and `InstallCertInWindowsStore` (`:172`, `:185`).
8. **Fiscal day open** — `OpenDay()`; **status** — `GetStatus()`; **close** — `CloseDay()`;
   `IsFiscalDayClosed` tests `FiscalDayStatus` containing `"Closed"`.
9. **Submission** — the live path is **`TransactM(...)`, not `SubmitReceipt`**. Parameter
   order: `(currency, email, invoiceNo, customerName, customerVat, address, phone, tin,
   amount, taxAmount, flag, comment, originalInvoiceNo, itemsXml, currenciesXml)`.
   `InvoiceFlag`: `"01"` sale, `"02"` credit note, `"03"` debit note.
10. **Response/signature** — `Data` XML is parsed for `QRCode`, `FiscalDayNo`,
    `ReceiptGlobalNo`, `DeviceID`, `SyncState`, and the receipt device signature/hash.
    Envelope `Code == "1"` means success. Adapter returns
    `FiscalResult { Ok, Code, Message, DataXml, QrUrl, DeviceHash, FiscalDayNo, ReceiptGlobalNo, SerialNumber, PendingSync }`.
11. **Receipt numbering** — `InvoiceNumbers.Next` / `NextCreditNote`
    (`CheckoutWindow.xaml.cs:248-253`) allocate the invoice number **before** fiscalisation
    and never reuse it (avoiding RCPT013).
12. **Trigger and ordering** — `CheckoutWindow.xaml.cs:229` `Fiscalize_Click`, on the
    "FISCALIZE & PRINT" button enabled once tender is chosen (`:220`). Fiscal-day check
    at `:265`; engine I/O off-thread via `Task.Run` (`:263`). Success order is
    **fiscalise → journal → stock → print**; on failure (`:304`) nothing is recorded,
    journalled or stock-updated and the window stays open for retry.
    This is the **inverse** of ClubStack D5's inventory-then-finalise order.
13. **Offline** — response `SyncState == "pending"` sets `PendingSync = true` and journals
    `Submitted = false`; `SubmissionService` wired at `App.xaml.cs:102`
    (`Journal = ReceiptJournal.Load()` at `:101`).
14. **Credit/debit notes** — `flag` `"02"`/`"03"` plus `originalInvoiceNo`.
15. **Errors/retries** — `SemaphoreSlim` gate with `GATE_TIMEOUT_MS = 15000`;
    failed fiscalisation is simply retried by the cashier.
16. **Counters** — DLL-internal `LastReceiptGlobalNo` / `LastFiscalDayNo` in `Stack.db`.
17. **QR** — `QRCode` element in the response `Data` XML, surfaced via `FiscalResult.QrUrl`.
18. **Sale → fiscal mapping** — `BuildItemsXml` emits `ITEMCODE` (= `HsCode`),
    `ITEMNAME1/2`, `QTY`, `PRICE`, `AMT`, `TAX`, `TAXR`, `TAXID`.
    `BuildCurrenciesXml` emits a **single** `<Currency>` with `Amount = Subtotal`, `Rate = 1`.
19. **Persistence** — `ReceiptJournal.cs` (4.3 KB) + `HoldsStore.cs` file journals;
    `config.ini` is the configuration store.
20. **Signing** — yes, internal: `Certificates.cs`, `DataProtection.cs` (DPAPI),
    `LicenseCore.cs` (ECDSA P-256) and `ZimraGateway.cs` (mTLS + signature handling).

`ZimraDirectApi.cs` is **not** a parallel receipt client — it is used only for
certificate bootstrap.

## 19. Payment / tax mappings — **CONFLICT, PM DECISION REQUIRED**

**Payment `[INSPECTION]`.** The working application **never transmits tender type to
the DLL.** `PosSale.PaymentMethod` (CASH/CARD/MOBILE) is local-only, and
`BuildCurrenciesXml` emits a single aggregate `<Currency>` with `Amount = Subtotal`,
`Rate = 1`. ClubStack's directive requires cash, card, account and split payments
each to be represented and explicitly forbids collapsing multiple payment methods.

**Tax `[INSPECTION]`.** The working application is **VAT-inclusive only**:
`PosItem.Tax = gross - gross/(1 + rate)` and `InvoiceTotal == Subtotal`, with
`TaxId = 0` letting the engine choose the bracket. ClubStack D5 supports three
treatments (inclusive, exclusive, zero-rated). `config.ini` confirms
`VATFLAG=1` (inclusive) with `VATA=0.155` and tax IDs `515` standard / `2` zero / `1` exempt.

These two gaps are the "working application vs ClubStack specification" conflict
the PM defined as a STOP condition.

## 33. Failures encountered, root causes, and fixes

**Failure 1 — initial assumption of a hard version conflict. `[EMPIRICAL]`**
*Root cause:* I inferred from `net48` vs `net10.0` that the DLL could not be
consumed, without testing it. *Result:* **the inference was wrong.** A `net10.0`
project references the `net48` DLL and compiles with **0 warnings, 0 errors**; the
DLL then constructed and initialised successfully (`IsInitialized=True`).

**Failure 2 — runtime `FileNotFoundException`. `[EMPIRICAL]`**
*Symptom:* `GetStatus()` threw
`Could not load file or assembly 'System.Security.Permissions, Version=0.0.0.0'`
from `Newtonsoft.Json.Serialization.JsonTypeReflector.get_DynamicCodeGeneration()`
(reached via `FiscalStackZW.BuildResponse`, `FiscalStackZW.cs:532`).
*Root cause:* the DLL's bundled `Newtonsoft.Json` **13.0.0** .NET Framework asset
references the .NET Framework–only `System.Security.Permissions`, which does not
exist in .NET 10. Note this also masked the real error, because `GetStatus()` was
already on a failure path and the JSON serializer itself threw while formatting it.
*Fix:* override the dependency graph with modern NuGet assets —
`Newtonsoft.Json` 13.0.3, `System.Data.SQLite.Core` 1.0.119,
`BouncyCastle.Cryptography` 2.4.0. *Verified:* `GetStatus()` then returned a
well-formed success envelope
`{"Code":"1","Message":"Local status (ZIMRA not reachable)","Data":"{...}"}`.
**The PM's "version conflict" STOP condition is therefore cleared** — the DLL does
load and run in ClubStack's host, and hosting is feasible.

**Failure 3 — every fiscalisation call is license-gated. `[EMPIRICAL]`**
*Symptom:* `TransactM(...)` with a well-formed sale returned
`{"Code":"0","Message":"License required: License key is malformed (expected 100 characters).","Data":""}`.
*Related:* `GetLicense()` returned
`<Status>License Status: Invalid</Status> ... <Message>License key is malformed (expected 100 characters).</Message>`.
*Root cause:* `LicenseCore.cs` requires a device-bound license — a 100-character
base64url payload over a **serial-fingerprinted** device (`FSTK-00000001`), signed
**ECDSA P-256** against a vendor public key. Default config has `LICENSEMODE=OFFLINE`,
`LICENSEGRACE=7`, `LICENSEKEY=` empty. *No fix is available to me:* signing needs
the vendor's private key, and the DLL's `LicenseCrypto.SignPayload` is a generator
whose embedded key is verification-only. **This is blocker 1.**

**Failure 4 — subagent infrastructure.** `[INSPECTION]`
`Cannot connect to API: Connect Timeout Error` killed two delegated inspections of
`FiscalStackZWPOS.App`; that work was completed by direct reads and greps instead.

**Defects found in the DLL and reported, not fixed** (the PM forbade rewriting it):
- `ZimraGateway` reassigns `HttpClient.Timeout` on every request, so every request
  after the first fails — **the online path is broken as shipped**.
- SQLite schema initialisation creates an index before its columns on a fresh
  database; the constructor swallows the exception.
- `BackupClient` defaults to plaintext `http://161.97.115.59:5010` with an
  unencrypted `x-api-key`.
- The constructor sets `Thread.CurrentThread.CurrentCulture/UICulture` to `en-GB`.
- `ServicePointManager.SecurityProtocol` is mutated process-wide.
- Heavy static mutable state; synchronous-over-asynchronous; no `CancellationToken`;
  COM `ClassInterface.AutoDual`.

## 34. Security considerations

- **Licence/private material:** the license key is device-bound, so it must be
  provisioned per device and must never reach the SPA.
- **Certificate handling:** private keys are DPAPI-protected by the DLL; an
  administrative renewal flow must stay server-side.
- **Backup channel:** the shipped plaintext HTTP + cleartext API key default is an
  unacceptable default for a fiscal device and should be disabled or overridden.
- **Culture mutation:** hosting the DLL in the API process would change the
  process-wide culture and `SecurityProtocol`, so it must be a singleton adapter
  invoked off the request path, as the reference app does.
- **No secrets** were copied into the repository, and none were logged.

directly rather than guessed. One of the anticipated STOP conditions was

requirements; and because no fiscalisation permissions are specified. Each of
these is a STOP condition the PM defined in advance.
