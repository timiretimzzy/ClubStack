## 6. Tax configuration verification

`[INSPECTION]` **Incoherent — and worse than previously characterised.** The engine's own
`SubmitReceipt` diagnostic enumerates the brackets it will actually use:

```
DEVICE TAX: id=515 name=Zero Rated pct=0.155
DEVICE TAX: id=2   name=Exempt      pct=0
DEVICE TAX: id=1   name=Zero Rated  pct=0
DEVICE TAX: id=515 name=Standard    pct=0
DEVICE TAX: id=5   name=High        pct=0
DEVICE TAX: id=1   name=None        pct=0
```

Three distinct defects are visible:

1. **The rate sits on a misnamed bracket.** The only non-zero rate, `0.155`, is attached to
   the bracket named `Zero Rated`, while the bracket named `Standard` carries `0`.
2. **Tax IDs are duplicated across contradictory brackets.** ID `515` is assigned to *both*
   `Zero Rated 0.155` and `Standard 0`; ID `1` is assigned to *both* `Zero Rated 0` and
   `None 0`. A tax ID therefore does not identify a single bracket.
3. **The configured standard-rated ID points at the wrong bracket.** `TAXIDSTANDARDRATED = 515`,
   and `515` resolves to `Zero Rated 0.155` *and* `Standard 0`.

The consequence is visible in the engine's item mapping:

```
ITEM: name=Widget TaxR=0.155 normRate=15.5 -> QualityTaxId=515
```

A standard-rated ClubStack line would be fiscalised under tax ID `515`, which the device
registers as **Zero Rated**. The receipt summary confirms the arithmetic runs through
(`amount=20.00 tax=2.69`, `taxPercent=15.5`), so the *amount* is right while the *tax
bracket identity* is wrong.

This is a **device-side configuration defect, not a ClubStack defect.** The ClubStack
resolver fix from the finalization session is correct and was not altered. Correcting
ClubStack's authoritative tax to match this device would mean misreporting a standard-rated
line as zero-rated to ZIMRA, which the directive forbids and which no implementation change
could legitimately justify. No tax rule was invented and no tax value was changed.
