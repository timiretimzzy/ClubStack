## 7. Device registration through ClubStack

**This is where verification stopped.**

`[INSPECTION]` The engine exposes a full certificate and registration lifecycle. Reflecting
over the real `FiscalStackZW.dll` shows these public methods:

| Engine method | Purpose | Exposed by ClubStack? |
| --- | --- | --- |
| `GenerateDeviceCertificates(serial, activationKey, deviceId)` | Build the certificate/CSR bundle | **No** |
| `VerifyCertificateDetails(serial, activationKey, deviceId, folder)` | Verify installed material | **No** |
| `RegisterDeviceWithZimra(activationKey, serial, deviceId)` | Register the device with ZIMRA | **No** |
| `GetCertificateDetails()` | Read certificate state | Yes (status only) |
| `ApplyDeviceSettings(folder, deviceId, serial, activationKey)` | **Consume** an existing manifest | Yes |
| `SetLicense(licenseKey)` | Apply license | Yes |

`CertificateUtility` confirms the intended order: `Generate` -> `CreateCsr` ->
`ImportFromServer` -> `RebuildPfxWithChain` -> `LoadManifest`, writing a `manifest.json`
that `ApplyDeviceSettings` then requires.

`[INSPECTION]` The manifest the engine expects carries: `SerialNumber`, `DeviceID`, `TIN`,
`VATNumber`, `CompanyName`, `ActivationKey`, `CertificateFolder`,
`CACertificateThumbprint`, `DeviceCertificateThumbprint`, `ServerCertificateThumbprint`,
`DeviceCertificateSubject`, `ServerCertificateSubject`, `CertificateValidTill`,
`GeneratedAt`.

**ClubStack can consume a certificate manifest but has no way to produce one.** Every step
that creates it — certificate generation and device registration — is absent from
`IFiscalisationGateway`. The only ways to close the gap are both forbidden:

- call `GenerateDeviceCertificates` / `RegisterDeviceWithZimra` directly, which is exactly
  the "bypass the ClubStack fiscalisation abstraction" that Part 15 prohibits; or
- add those capabilities to ClubStack, which is an implementation change the directive did
  not authorise, and which would then run `ImportFromServer` against an endpoint still
  pointing at **production**.

`ImportFromServer` also implies the engine must contact ZIMRA to obtain a signed
certificate — so provisioning cannot be completed offline either.

**No certificate was generated, no registration was attempted, and no ZIMRA request was
issued by this session.**

## 26. Root causes

**Primary — a capability gap, not a bug.** ClubStack's fiscalisation abstraction models a
*already-provisioned* device. It can consume a certificate manifest and apply a license, but
it exposes no way to *create* the certificate material or register the device. Provisioning
therefore requires engine capabilities (`GenerateDeviceCertificates`,
`RegisterDeviceWithZimra`) that the abstraction deliberately does not wrap, and Part 15
forbids reaching past the abstraction to reach them.

**Contributing — an ordering deadlock created by that gap.** The license is bound to serial
`HOYOTEST`; the serial is only settable via `ApplyDeviceSettings`; and `ApplyDeviceSettings`
requires a manifest that only the unwrapped steps can produce. Neither step can be
completed first through ClubStack alone.

**Contributing — the device is still pointed at production.** `ServerUrl` is
`https://fdms.zimra.co.zw` and no ClubStack-exposed call can select
`https://fdmstest.zimra.co.zw`. Even had provisioning succeeded, `ImportFromServer` and any
day or receipt operation would have targeted production ZIMRA. This alone is disqualifying
under the standing instruction not to send test traffic to production.

**Underlying — the supplied test device was not provisioned on this host.** The PM's
statement that a test device "has now been provisioned" does not match the machine: the
engine still holds the old development identity, no certificate manifest exists, and the
license cannot bind to it.

## 27. Fixes

**No product fix was made, and none should be made from this session.**

Closing the gap requires a decision that is the PM's, not the implementer's, because each
option carries a consequence the directive did not authorise:

1. **Provision out of band** (no code change) — have the vendor or ZIMRA generate the
   certificate material and place a valid `manifest.json` in
   `C:\FiscalStackZW certificates`, and confirm the device is pointed at
   `https://fdmstest.zimra.co.zw`. ClubStack's existing code would then work unchanged.
2. **Authorise a specific ClubStack change** — add certificate generation and device
   registration to `IFiscalisationGateway`, the service, and the API, as a first-class
   provisioning capability. This is defensible design (the gap is real) but is a new
   feature, and it must not be switched on while the engine points at production.

Fabricating a `manifest.json`, hand-editing `config.ini` to repoint the endpoints, or
patching the DLL were all rejected: they would fake the provisioning the test exists to
prove, and the first two are explicitly forbidden.

**The only change made was creating the empty `C:\FiscalStackZW certificates` directory**,
which ClubStack's own adapter requires to exist before it will call the engine.
