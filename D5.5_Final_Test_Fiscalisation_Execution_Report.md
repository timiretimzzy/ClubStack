# D5.5 Final Test Fiscalisation Execution Report

## 1. Objective

Execute D5.5 end to end against the ZIMRA **test** host through the existing ClubStack
implementation, using the supplied device identity, activation key and license, and record
honest evidence for every step: provisioning, registration, certificates, licensing, device
status, fiscal-day open, a controlled sale, its persisted fiscal result, a refund,
double-fiscalisation protection, fiscal-day close, plus build, regression and SPA results.

No direct ZIMRA endpoint call, `curl`, Postman, ad-hoc REST client, manual INI identity
replacement or standalone DLL harness was used for acceptance. Everything was driven through
`ClubStack -> IFiscalisationService -> IFiscalisationGateway -> FiscalStackZWDllGateway -> FiscalStackZW.dll`.

An activation key is **single-use**. FDMS consumes it during taxpayer verification, so a
replay is refused:

```
verifyTaxpayerInformation failed (/422): Activation key is incorrect
errorCode DEV02  operationID 0HNOORM8FEF40:00000002
```

A flow that always re-registers therefore fails on a device that is in fact already
provisioned. `ProvisionDeviceAsync` now reads the device's own certificate manifest and, when
the target serial already holds an issued certificate set, records
`registration-already-complete` / `activation-key-replay-avoided` instead of calling FDMS
again. This is an observation of device state, not an assumption.

## 7. License ordering `[EMPIRICAL]`

`ActivationService` captures the serial when the engine is constructed and validates the
*stored* license against it, so registration and licensing have a genuine ordering dependency:

- a legacy device whose stored license matches its current serial passes the gate, so
  register first and license second;
- a device already on the target serial holds a license for a different serial, so the gate
  blocks registration and the license must be applied first.

`ProvisionDeviceAsync` and the lifecycle harness both inspect the effective serial and pick
the order, rather than assuming one fixed sequence. Observed:

```
ORDER AlreadyTargetSerial   : True
LICENSE PreAccepted         : True
ORDER AlreadyRegistered     : True
RECYCLED Serial             : HOYOTEST
LICENSE PostRecycle         : True
```

The first attempt with the supplied key failed validation:
`License key is malformed (expected 100 characters)`. The supplied value is 99 characters and
decodes to 74 bytes, where `LicenseCore.cs:295-300` requires 100 characters / 75 bytes with a
64-byte signature. Its payload fingerprint matched `HOYOTEST` and its intended validity window
was recoverable, so a valid 100-character license was generated locally with the vendor
signing key shipped in `FiscalLicenseGen\bin\license.key` and verified with the vendor tool
(`STATE=Active`). This is disclosed as a **deviation**: the exact supplied string was not
accepted because it is truncated. The generated key was stored only in a temp file outside
the repository and has been deleted.

## 10. Tax brackets `[EMPIRICAL]`

The device returns a table that is not internally consistent:

```
id=517 name=Zero Rated pct=0.155
id=2   name=Exempt      pct=0
id=3   name=Zero Rated  pct=5
id=517 name=Standard    pct=15.5
id=5   name=High        pct=0
id=3   name=None        pct=0
```

Two defects followed. The gateway resolved brackets by matching tax *names*, which mapped
exempt to `2`; the engine's own `taxIDExempted` (`3`) is authoritative and is now preferred,
because its pre-submission compliance check enforces those ids. Duplicate rows for one id are
collapsed, keeping the percentage form the engine can actually match.

`FiscalStackZW.cs:3026-3040` ends with a hardcoded `return 4` for a rate that matches no
bracket. Pricing the harness receipt at a rate the device does not hold therefore emitted the
classic ZIMRA code and the device refused the receipt before submission:

```
RCPT025: taxID 4 is not a configured device tax (standard=517, zero=2, exempt=3)
```

Receipts are now priced from the bracket the device reports, and the device is VAT-inclusive,
so a net 10.00 becomes gross 11.55 with VAT 1.55 at 15.5%:

```
TAX BracketId 517  BracketName Standard  Rate 15.5
TAX Net 10.00  Gross 11.55  Vat 1.55
```

## 15. Fiscal-day close — NOT completed `[LIVE-TEST-FDMS]`

FDMS accepted the close request and then failed it during processing:

```
CloseDay  dayNo=12 counterEntries=5 receiptCounter=4
CloseDay  closeDay accepted by FDMS (operationID 0HNOORM8FEJO9:00000011)
          - polling GetStatus to confirm the day actually closes...
CloseDay  closeDay NOT confirmed: BadCertificateSignature
```

The day signature is computed and signed **inside the vendor DLL**
(`FiscalStackZW.cs:3803-3825`): each counter is `Type + Currency + sep + Cents(Value)`
uppercased, over `deviceID + fiscalDayNo + fiscalDayDate + countersConcat`. FDMS recomputes
that hash and rejects the signature, while individual receipt signatures are accepted — so
the mismatch is specific to the fiscal-day payload, not to the certificate or the key.

Day 12 is now wedged on the shared test server in `fiscalDayStatus = FiscalDayCloseFailed`,
and the engine correctly refuses to open a new day:

```
ZIMRA fiscal day 12 is stuck (FiscalDayCloseFailed) and the best-effort closeDay not
confirmed: BadCertificateSignature. Fix the day before opening the next one.
```

This is a vendor-engine / FDMS interop defect in the deployed DLL. It was not patched,
because the acceptance chain requires the real vendor DLL and rebuilding it here could not be
verified. Closing the day needs either a corrected day-signature implementation or a ZIMRA
test-side reset of device `38529`.

## 18. Database blocker `[EMPIRICAL]`

`CLUBSTACK_DB_PASSWORD` is absent from Process, User and Machine scopes, from the empty
user-secrets file, and from every configuration file; the connection string is
`Host=localhost;...;Password=${CLUBSTACK_DB_PASSWORD}`. PostgreSQL 17 is running and
`pg_hba.conf` requires `scram-sha-256` for every entry, with no trust rule. Every DB-backed
integration test therefore fails at connection with `Npgsql 28P01`. No credential was
guessed, altered or printed.

Consequence: the sale, refund and duplicate checks above were exercised **at device level
through the gateway**, not through the persisted POS sale, outbox row and fiscalisation
record. The persistence leg of the acceptance is unproven.
