## 3. What was built

- `FiscalisationEntity` plus `fiscalisations` table. Unique `InvoiceNumber`;
  filtered unique `SaleId` where `RefundId IS NULL`; status and fiscal-day indexes;
  concurrency-token configuration.
- `FiscalisationRequiredEvent` — deliberately narrow (fiscalisation id, sale id,
  refund id, correlation id). No amounts or tenders in the message payload.
- `FiscalisationRequirementWriter` — writes the pending document and its outbox
  message in the same transaction as the sale or refund commit. The tender
  breakdown is snapshotted at that moment.
- `FiscalisationProcessor` plus two handlers, one per event type
  (`FiscalisationOutboxHandler`, `FiscalisationCreditNoteHandler`).
- `FiscalisationService` — device status/configuration, fiscal day control, document
  search, retry, engine-queue flush, and the new device administration operations.
- `FiscalStackZWDllGateway` — singleton adapter, `SemaphoreSlim` gate, blocking calls
  through `Task.Run`, envelope/XML/JSON parsing.
- `FiscalisationXmlBuilder` — item and currency XML.
- API: `/api/v1/fiscalisation` with device, day, document and administration routes.
- SPA: `FiscalisationPage` and `FiscalStatusForSale`.
- Permissions: six distinct permissions, mapped to Club Manager and Finance Officer.

## 4. State machine

`NotRequired → Pending → Submitted → Fiscalised`, with `PendingRetry` for deferred
work and `Failed` as a terminal error state.

Rules enforced in the worker:

- A document already `Fiscalised` is a no-op, so retries never re-transact.
- A document the engine already holds (`ReceiptGlobalNo` set, or `PendingSync`) has
  its engine queue flushed rather than being submitted a second time.
- A closed fiscal day **defers** the attempt. The worker never opens a day
  implicitly; that requires an authorised operator.
- Device failure defers and keeps the document owed.

## 5. Tender and tax handling (PM decisions 2 and 3)

`[TEST-SEAM]` The engine receives one aggregate `CurrenciesReceived` line because
that is the only representation its API supports. The full ClubStack tender
breakdown — method code, method name, kind, amount, external reference — is stored on
the fiscal record, and the mapping is recorded as `aggregate-single-currency` so the
representation is never ambiguous at audit time.

`[TEST-SEAM]` Document amounts are taken from ClubStack's own calculated sale. No
re-derivation or re-rating occurs in the adapter.

`[TEST-SEAM]` Tax identifiers are read from the device's own configuration table,
never hard-coded. Resolution requires a name match *and* a rate that agrees with the
treatment, and returns `0` (meaning "the engine selects") whenever the table is
ambiguous — which is the observed state of an unregistered device.

`[INSPECTION]` **Outstanding judgement call:** the D5 refund snapshot does not carry
per-line tax. `FiscalDocumentBuilder` derives refund tax proportionally from the sale
tax total. This satisfies the arithmetic but is not a per-line reconstruction, and it
should be confirmed against the PM's intent for mixed-rate refunds before acceptance.

## 6. The two defects fixed in this session

1. **Outbox worker discarded every write.** `FiscalisationProcessor.ProcessAsync`
   loaded the fiscal record with `AsNoTracking()` and then mutated it and called
   `SaveChangesAsync`. Nothing persisted, so no document ever reached `Fiscalised`
   and the receipt was lost. Caught by
   `Worker_fiscalises_a_pending_sale_and_persists_the_device_receipt`. Fixed by
   tracking the entity.
2. **Engine had no reachable management surface.** `SetLicenseAsync` and
   `UpdateConfigurationAsync` existed on the gateway but no service or API method
   called them, so device provisioning was not actually possible from ClubStack.
   Added at the service and API layers, permission-gated and audited.

Both were found by tests written after the fact, not by inspection alone.

## 7. Security posture

`[TEST-SEAM]` Verified by test, not assertion:

- The license key reaches the engine and is never persisted, logged or audited.
- The activation key is forwarded to the engine only; it is excluded from the
  configuration audit metadata.
- No read route returns a license key or activation key. `device/status` and
  `device/configuration` responses were asserted not to contain either string.
- The audit trail for device administration records the action, the operator and the
  identity fields — never the key material.
- `license.key` remains at its original external path
  (`FiscalLicenseGen\bin\license.key`) and is not in the repository.

## 8. Empirical device evidence

`[EMPIRICAL]` The production adapter loads the real net48 `FiscalStackZW.dll` in the
net10 host and reads the device successfully. Five read-only tests in
`FiscalStackDeviceLoadTests` cover: DLL presence, device status, device
configuration with tax-identifier resolution, side-effect-free pending count, and
concurrent calls under the adapter gate. They skip cleanly when the DLL is absent and
never transact, open or close a day.

Earlier direct-probe findings still hold: license active, `OpenDay` returns fiscal day
1, `TransactM` returns a receipt with `SyncState: pending`, and the device is offline
from FDMS. `GetUnProcessedTransactions(..., 1, 1).Data.TotalRecords` is the
side-effect-free pending counter.

`[INSPECTION]` One correction to the earlier investigation: the `IFiscalStackZW`
interface declares a `TransactM` overload that the concrete
`FiscalStackZW.FiscalStackZW` class does not implement. The adapter deliberately
targets the concrete class, whose real signature is:

```
TransactM(Currency, CustomerEmail, InvoiceNumber, CustomerRegisteredName,
          CustomerVATNumber, CustomerFullAddress, CustomerTelephoneNumber,
          CustomerTIN, InvoiceAmount, InvoiceTaxAmount, InvoiceFlag,
          InvoiceComment, OriginalInvoiceNumber, ItemsXML, Currencies)
```

## 9. Testing notes worth carrying forward

The `[Collection("Database")]` tests share one scratch database, so the outbox job
drains messages belonging to sibling tests. Assertions are therefore written against
**this test's own document**, never a global count: documents are matched by invoice
number, audit rows by a per-test actor id, and status filters are compared as deltas.
A test that asserts an absolute total in this collection will be order-dependent and
should be treated as a defect.

## 10. Outstanding — must be closed before acceptance

1. `[LIVE-FDMS]` **Registered-device transaction.** Needs a valid device id,
   activation key, taxpayer details, device certificates and reachable FDMS. Nothing
   in this session proves the live path. The offline receipt obtained during
   investigation is not evidence of FDMS acceptance.
2. `[LIVE-FDMS]` Verify the engine's VAT computation against a ClubStack-calculated
   tax amount on a registered device. The earlier probe showed the engine recomputing
   2.69 as 2.68; DECISION 3 forbids adjusting ClubStack's figure, so the
   authoritative-value behaviour under a real device must be observed and recorded.
3. `[INSPECTION]` Confirm the proportional refund-tax treatment for mixed-rate refunds
   (§5).
4. `[LIVE-FDMS]` Device provisioning with a real certificate folder. The
   `UpdateConfigurationAsync` path is exercised only against a fake gateway, because
   this host has no `C:\FiscalStackZW certificates` directory.
5. `RefundId` has no explicit foreign key or unique filtered index. The
   one-credit-note-per-refund invariant is enforced in code and by the filtered
   `SaleId` index, but the database does not independently reject a duplicate refund
   document the way it rejects a duplicate invoice. Worth adding before acceptance.

## 11. Do not delete

`C:\ProgramData\FiscalStackZW` holds the active development license, device
configuration, database and logs. It is required for provisioning and for the
empirical tests. Do not remove it before the handoff in §10.
