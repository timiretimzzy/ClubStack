## 2. Database credential configuration mechanism used

The password is stored in the **user-scope environment** on this machine:

```
HKCU\Environment\CLUBSTACK_DB_PASSWORD   (21 characters)
```

Configured once with:

```powershell
[Environment]::SetEnvironmentVariable('CLUBSTACK_DB_PASSWORD', '<password>', 'User')
```

Why this mechanism was chosen:

- `ConfigurationSecretExpander.Expand` resolves the `${CLUBSTACK_DB_PASSWORD}` token in the
  committed connection string **from the process environment**. The `secretValues` callback
  it exposes for user-secrets is dead code — no caller passes it, and no project wires
  `AddUserSecrets`. User-secrets were therefore not a working channel without a code change.
- `PostgreSqlTestFixture.BuildAdminConnectionString` and
  `ClubStackDbContextDesignTimeFactory` also read the value with
  `Environment.GetEnvironmentVariable`. A user-scope variable satisfies every existing reader
  at once, so no application code was modified.
- It is machine-local, registry-backed, and outside the repository. It is not in git, source,
  `appsettings.json`, test fixtures, documentation, reports, generated artifacts, API
  responses or console output.

The value was never printed. Only its presence and length were reported.

## 3. The user will not need to supply the password again

Confirmed. `HKCU\Environment` is read by Windows when it launches any new process for this
user, so every future shell, `dotnet build`, `dotnet test` and application start resolves
`CLUBSTACK_DB_PASSWORD` automatically. A new terminal is only required after *changing* the
value, because an already-running shell keeps its own process environment.

## 16. Deferred CloseDay / DLL issue

**Deferred at PM direction. Not a blocker. D5.5 is not blocked.**

`Fiscal-day CloseDay currently fails with BadCertificateSignature` because of the deployed
vendor DLL's fiscal-day signature behaviour: the day signature is computed and signed inside
`FiscalStackZW.dll`, FDMS recomputes it and rejects it, while individual receipt signatures
are accepted. TEST device `38529` is consequently in `FiscalDayCloseFailed`.

This session did not attempt a workaround, did not call `CloseDay` again, did not open
another fiscal day, did not patch the vendor DLL, and did not fabricate a successful close.
It is recorded as a known deferred engineering issue pending the PM's fix to the DLL.
